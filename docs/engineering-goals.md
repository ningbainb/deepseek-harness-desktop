# DeepSeek Harness Desktop 工程目标

## 目标与依据

本工程以“桌面版可以稳定启动、可靠完成工作、保存并恢复用户数据”为首要交付目标，在现有 Electron 壳、官方 DSH Runtime 和插件体系上补齐需求。实施顺序为稳定性、访问隔离、上下文与项目能力、体验完善。

需求来源为 [飞书需求库](https://txbpzdory9d.feishu.cn/wiki/MjaLw5u6piObmRkDiWtcyxk1nhb)，依据为 [36 条需求核查快照](archive/2026-09-07-feishu-recovery-audit.md)，其中 R28 不在工程范围内。下文 R01–R36 对应快照序号，不是飞书 record ID；后续执行以工程目标 G01–G09 及其工作项编号跟踪，回写飞书前必须核对原记录 ID 和标题。

本文是实施目标和验收契约，不表示功能已修复或正式排期。需求库的“已完成”状态、代码存在、单元测试通过和真实应用验收是不同证据；本机未安装官方 SDK 依赖，涉及内核能力的判断仍需用锁定版本的官方 NPM 包验证。现有测试结果只引用核查快照，不作为未来版本的通过记录。

## 项目适配评估

项目边界以 [桌面架构](desktop.md)、[Runtime 支持政策](runtime-support-policy.md)、[兼容政策](compatibility-policy.md) 和 [仓库规则](../AGENTS.md) 为准。多数需求适合扩展现有模块，默认不增加新插件包或独立后台服务。

| 已有基础 | 本轮评估 | 对工程目标的影响 |
| --- | --- | --- |
| Desktop 启动、阶段记录、重试、事务修复和更新器 | 已有 [startup-phase.mjs](../apps/dsh-desktop/src/startup-phase.mjs) 等基础，不能把“卡 88%”直接等同于没有阶段管理 | G01 以故障注入、超时联动和离线恢复闭环为主，不重建启动系统 |
| 环境变量代理解析 | [electron-app.mjs](../apps/dsh-desktop/src/electron-app.mjs) 已读取 HTTP_PROXY、HTTPS_PROXY、ALL_PROXY、NO_PROXY 并设置 Electron session | G07 验证各传输层是否实际生效，再补配置入口和分层策略 |
| 用户作用域、记忆、Prompt、模型偏好 | 首版模块已存在，授权、实际生效和公开 SDK 可用性仍需验证 | G03–G05 以完成集成为主，避免重复实现官方状态管理 |
| 插件事务安装、可恢复存档 | 已有 [plugins.mjs](../apps/dsh-desktop/src/extensions/plugins.mjs) 和 [user-plugin-archive.mjs](../apps/dsh-desktop/src/user-plugin-archive.mjs) | G06 复用事务能力实现修复入口，不直接清空用户目录 |
| 图片处理、皮肤、余额、轮次导航、导入 | 功能入口与部分测试存在，复合需求尚未逐项验收 | G02、G05、G09 拆分工作项，分别提供用户场景证据 |

静态检查发现的滚动条热区重叠、模型标签刷新不足，是可验证的故障假设，不替代现场根因确认。未搜索到实现也不等于官方 Runtime 不支持；内核相关工作先做能力验证。

## 开源参考与采用原则

各目标中的开源参考用于降低复杂实现的试错成本。链接指向项目官方源码或文档；所述机制已查阅，但本项目的适配方案属于工程建议，尚未完成集成验证。滚动更新的文档与 main 分支不是锁定版本，进入对应工作项时记录选定 tag/commit、来源文件、适配差异和验证结果。

优先借鉴状态管理、取消、授权和恢复算法，再考虑引入小型依赖。默认复用本仓库已有模块，不整套引入另一套 Agent Runtime、Python 服务、权限服务器或向量数据库。若候选依赖确有必要，先验证现有框架适配、安装及打包增量、空闲与峰值内存、Windows 支持，再决定是否采用；本机按单工作项验证，不批量克隆参考仓库。

参考项目不能扩大 DSH 的公开能力边界：插件仍只通过官方 NPM SDK、`cordis.patch.yml` 和 profile 挂载；官方源码 checkout 零写入。采用外部源码或依赖时核对所选版本的 LICENSE、NOTICE 及传递依赖要求，保留必要署名；本文不把“开源”视为无条件复制许可。

## 工程优先级与规模

P0 表示启动、核心工作流或数据访问边界的发布风险；P1 表示已有替代方式但影响主要体验；P2 表示可用性完善或独立增量。此处是工程排序，不改写用户原始优先级。

规模为相对工作量：S 是单模块修订，M 是跨模块联调，L 是跨进程、数据迁移或故障恢复。不是人日估算；负责人、可用工时及真实测试环境确认前不承诺交付日期。

| 目标 | 交付结果 | 优先级 | 规模 | 关键依赖 |
| --- | --- | --- | --- | --- |
| G01 启动与运行恢复 | 无网络、坏插件、更新失败均有明确终态，工具调用可靠 | P0 | L | 官方 Runtime 可解析、故障注入环境 |
| G02 基础交互与附件 | 滚动、窗口、图片和皮肤不阻塞操作 | P0/P1 | M | 可运行的打包应用和真实窗口事件 |
| G03 模型一致性 | 当前实际模型和各端显示一致，偏好不破坏官方选择逻辑 | P0/P1 | M | 官方模型目录、选择 API、事件能力验证 |
| G04 用户访问隔离 | 配对主体间资源不泄露，撤销即时生效 | P0 | L | 统一资源归属、两设备验证 |
| G05 上下文连续性 | 记忆、Prompt、导入和压缩可解释、可恢复 | P1 | L | G04；官方 Prompt、Session、Compaction 契约 |
| G06 插件兼容与安全修复 | 安装失败可回滚，修复不会误删用户数据 | P0/P1 | L | G01；插件存档、Profile 解析 |
| G07 分层代理 | API、更新、市场和插件网络行为可配置并可诊断 | P1 | L | 各传输层及官方插件权限能力验证 |
| G08 工作目录迁移 | 项目换目录后旧历史可读，新任务落在正确目录 | P1 | L | G05；官方 Workspace 契约、G06 事务模式 |
| G09 功能说明与入口 | 技能、余额、宠物、看板和会话操作可理解 | P2 | S/M | 已有功能真实行为确认 |

## G01：启动、更新与运行恢复

**范围：R04、R05、R10、R12、R20、R21、R22 的启动和升级部分。** 承载模块为 Desktop runtime controller、startup phase、updater、安装器、terminal session 和 dsh-desktop-compat。

- G01.1：为新建空 Profile、正常启动、DNS 失败、更新禁用、坏插件、就绪探测超时建立可复现样例；将实际阶段、耗时和失败原因连到现有状态通道。
- G01.2：更新检查不阻塞主界面就绪；自动修复沿用有界重试和事务验证；无可用模型或无网络时进入可解释的本地恢复结果。临时禁用社区插件必须可见且可恢复，不能修改内置功能基线。
- G01.3：验证 Runtime 和工具子进程的 Windows 窗口隐藏，以及 SSH 面板的挂载和重启后可用性。子进程隐藏与内嵌终端显示分别处理。
- G01.4：验证空配置生成、正常工具模型、无工具模型及带工具历史的兼容行为。按明确的 provider capability 决策，不根据 MoE 架构或模型名称推断工具能力；不支持工具历史时明确报错或提供受控转换，不静默删历史。
- G01.5：重复升级和失败回滚保持一个有效安装入口；安装目录内新旧 Runtime 不混用，版本化下载缓存与重复安装实例分别统计。

**验收：** 各故障均在配置的超时及重试预算内进入 ready、可操作的恢复页或明确失败状态；不无限停留在进度百分比。更新 DNS 失败不阻止本地主界面使用；`--disable-updater` 的所有入口均受验证。连续 20 次工具调用无外部控制台闪现，SSH 内嵌终端仍可输入输出。重复升级两次后入口唯一、版本一致、原会话可读；中途失败可以回到原版本。预算数值在实现前基于当前启动基线确定并固化到测试。

**开源实现参考：** [XState 的 invoked actors](https://stately.ai/docs/invoke) 将异步任务与状态进入、退出及成功/失败转移绑定，可用于梳理现有 startup phase 和 runtime controller。建议为每次启动分配 attempt ID，写出阶段转移表，退出阶段后忽略旧结果；超时还必须主动取消请求、清理探测器并回收相关子进程，不能把丢弃 Promise 结果当作底层任务已经停止。采用方式为参考状态模型，暂不新增 XState 依赖。专项验证“第一次启动超时后迟到的 ready 事件不能覆盖第二次启动”，并记录超时后的进程与监听器数量。

## G02：基础交互、皮肤和附件可靠性

**范围：R01、R08、R09、R11、R13、R14 的附件与轮次导航、R24、R26、R27、R34。** 复用 Desktop window chrome/settings window/window factory、dsh-aionui-panel、Skin Center 和 dsh-web-ui-all。

- G02.1：复现设置滚动条与 resize handle 竞争，调整热区和事件归属；在保留边框缩放功能的同时保证滚动条和输入控件可操作。
- G02.2：将图片拖放拆为校验、解码、压缩、提交和清理阶段；成功、失败、取消均清理遮罩与临时对象。大图逐个或有界处理，校验像素尺寸及文件大小，避免并行解码放大内存峰值。
- G02.3：分别验收皮肤选择持久化、聊天区实时更新、零模糊时的背景效果；定位表面探测遗漏，不用全局透明样式掩盖问题。
- G02.4：为主窗口和扩展坞定义相对位置跟随、手动移动子窗、最大化还原、多显示器越界和关闭后的监听清理；保留现有独立操作能力。
- G02.5：补输入框随滚轮移动、暗色标签、侧栏重叠回归；验证复制路径、文件引用和上下轮导航。文档拖入的交付语义必须明确区分文件路径引用、预览和内容送模，不能把插入路径称为已解析 Word/PDF。

**验收：** Windows 100%、125%、150% 缩放下分别执行 20 次滚动条拖动，设置窗口不误移；边框缩放仍工作。小图、大图、坏图、取消、连续拖入及“大图后小图”均不锁死输入；每个失败样例无需刷新即可重试。切换皮肤并退出重进连续 5 次保留选择；扩展坞不越出可见显示器。长对话滚动不移动输入区域，导航落在正确用户轮次。R01、R08 作为保全项回归，不重写已有功能。

**开源实现参考：** [pica](https://github.com/nodeca/pica) 提供分块缩放和可配置 worker 并发，可作为现有图片压缩实现的对照。建议先补单图片队列、像素上限、取消令牌及 finally 清理，再以同一组大图比较现有方案与 pica；若收益成立，才评估按需加载依赖，并将并发显式设为 1。分块缩放不解决原图首次解码的内存峰值，仍须在解码前检查可获得的尺寸信息，对未知尺寸采取保守限制，释放 ImageBitmap、对象 URL 和中间画布。专项验证快速连续拖入、切会话取消和压缩失败后的资源回收，不能只比较压缩后文件大小。

## G03：模型选择和多端一致性

**范围：R02、R06、R25。** 复用 dsh-model-preferences 和 dsh-remote-web-ui，以官方 Session/ModelDirectory 为状态来源。

- G03.1：验证官方公开接口是否提供模型变更订阅。可用则订阅；不可用则在页面恢复可见、重连、打开选择器及选择成功后重新读取，并明确后台端的同步边界。不得虚构官方事件名称或使用常驻高频轮询。
- G03.2：处理跨窗口并发选择、切会话后的陈旧响应和请求失败；显示值以服务端确认结果为准。鸿蒙端无法切换与跨端标签不同是两个复现项。
- G03.3：置顶、排序、隐藏供应商只改变可选目录投影；当前已选模型、凭据、reasoning、能力和运行中的请求不被偏好设置破坏。
- G03.4：核对当前 `/model` 的客户端贡献点；若官方 SDK 无可用扩展入口，将“输入框偏好已支持、原生命令保持官方行为”作为明确能力边界，完整统一列为上游依赖，不冒充完成。

**验收：** 桌面两窗与手机同时打开同一会话；各端选择后，已连接可见端在正常测试网络下 2 秒内显示服务端确认值，重连后 2 秒内完成校准，此数值为拟定验收目标。若公开 API 无法支撑该目标，应在能力验证阶段报告阻塞并评审调整。模拟响应乱序不串会话，失败不会显示假成功。至少一台真实鸿蒙设备完成切换与发消息验证；桌面浏览器模拟不能替代该项。

**开源实现参考：** [TanStack Query 的请求取消](https://tanstack.com/query/latest/docs/framework/react/guides/query-cancellation) 展示了将 AbortSignal 传给实际请求的方式。建议借鉴其请求生命周期管理，在现有模型状态层用主体、Runtime 和 Session 标识隔离缓存，切换时取消旧查询，并用请求序号或服务端版本拒收陈旧响应；取消客户端查询不保证撤销服务端已执行的模型变更，仍须重新读取确认值。采用方式为参考机制，不为此另起 React 状态层或增加依赖；跨设备通知仍由 G03.1 的官方能力决定。专项验证“先切 A、再切 B，A 最后返回”以及撤销设备后缓存不可复用。

## G04：用户访问与数据边界

**范围：R15，以及 G03/G05/G08 引入的数据访问。** 复用 dsh-user-scope 和移动端受限 API，遵循 [安全边界](security-boundaries.md)。

区分三类主体：应用内资源归属、配对远程设备、操作系统用户。当前主 Runtime 可在同一 Windows 用户权限下运行；仅增加应用 owner ID 不能保证抵抗该 Windows 用户下可读磁盘的其他进程。需要强本地保密时，目标是独立 OS 账户及相应访问控制，不能用隐藏列表替代隔离。

- G04.1：列出 Workspace、Session、历史、搜索、附件、模型选择、记忆、Prompt、导入及 SSE 的授权矩阵；所有新入口检查资源归属，未知归属明确拒绝。
- G04.2：验证设备撤销、旧凭据复用、并发请求、现有流断开及缓存清理；共享与转移资源需要显式流程。
- G04.3：文档标明当前支持的本地主体切换方式；不存在完整登录切换流程时，将其作为新增设计项，不宣传已支持本地多账户。

**验收：** A/B 两主体和两设备对矩阵逐项交叉访问，未授权内容不得进入响应或流；撤销后新请求立即被拒绝，正常网络下既有流 2 秒内关闭。官方 loopback 边界保持有效，不能以开放完整 `/api` 解决手机接入。发现真实跨主体泄露时阻塞发布。

**开源实现参考：** [OpenFGA 的父子资源关系模型](https://openfga.dev/docs/modeling/parent-child) 可用于审查 Workspace、Session、附件的归属与访问关系。建议将授权判断集中到现有 dsh-user-scope，使用明确的主体、资源和操作参数；先确认父子归属一致，只有产品明确允许的共享规则才传播权限。采用方式为本地授权模型参考，不部署 OpenFGA 服务。namespace 或 owner 字段本身不是授权检查；SSE 建连和持续发送都需覆盖撤销流程，专项测试猜测资源 ID、跨父资源引用、旧缓存和已经打开的流。

## G05：记忆、Prompt、导入与压缩

**范围：R03、R18、R19、R31。** 复用 dsh-memory、dsh-personal-prompt、conversation-import 及官方 Compaction。

- G05.1：记忆坚持显式保存或确认写入；完成权限、增删查、损坏恢复和注入限额验证。限制以 [memory schema](../packages/dsh-memory/src/core/schema.ts) 为权威。
- G05.2：Prompt 的存储、作用域解析、启停和预览以 [config.ts](../packages/dsh-personal-prompt/src/core/config.ts) 为权威；修正文档示例与实现不一致处，验证历史配置读取和优先级。不把语言偏好描述为模型必然遵守的保证。
- G05.3：导入验证预览、去重、目标目录映射、失败重试和导入后续写。历史工具调用保持不可执行，原来源文件只读；“续写上下文”不等于跨产品恢复原运行时状态。
- G05.4：先确认通用 desktop profile 是否已经暴露官方 compact 命令；已有则补入口说明和状态反馈，没有则通过公开能力接入。压缩保留必要历史关联并报告失败，不通过删消息模拟压缩。

**验收：** Prompt、记忆在关闭或越权情况下不进入请求，限额和作用域正确；数据损坏不会静默清空。相同导入执行两次不重复会话，失败重试不产生半条记录；导入后消息进入预期 Workspace。压缩前后会话可继续、工具调用关系有效，失败可重试且原历史仍可读取。依赖 G04 的访问矩阵通过后才进入发布验收。

**开源实现参考：** 本目标分别参考记忆建模与上下文压缩，不替换官方会话执行器。

- 记忆与 Prompt：参考 [LangGraph 的记忆模型](https://docs.langchain.com/oss/python/concepts/memory) 对会话状态、跨会话 namespace 和条目 key 的区分。建议在现有 dsh-memory/config schema 上核对用户、项目、条目身份，读取先授权，再按配额选取注入内容；存储变更沿用版本化、损坏可恢复的本地流程。只借鉴数据模型，不安装 LangGraph/Python，也不把向量检索作为首版前置。专项验证同名项目、切主体、条目删除及关闭注入后不会残留旧上下文。
- 压缩与导入后的续写：参考 [OpenAI Codex 的 compact.rs](https://github.com/openai/codex/blob/main/codex-rs/core/src/compact.rs) 中用户消息收集、摘要及压缩历史构造的分工，用于设计 DSH 压缩前后的一致性样例。实际执行必须走官方 DSH Compaction 契约，不能直接移植 Rust 执行器、套用消息协议或写入官方数据库。专项验证摘要失败、工具调用与结果关联、压缩后追问、导入历史中的指令不会触发旧工具重放；界面显示当前处理阶段和失败原因，不声称摘要能无损保留全部历史。

## G06：插件事务、兼容与修复向导

**范围：R14 的插件管理及工具调度副本问题、R16、R23、R35、R36。** 复用现有安装事务、存档、修复与 [升级回滚契约](upgrade-and-rollback.md)。

- G06.1：验证安装、启用、停用、移除及失败回滚，确保官方 SDK 的运行时解析身份一致；仅检查版本号相同不足以排除两份模块导致的 Symbol 分裂。
- G06.2：修复入口先显示真实 Profile、插件加载位置、清理范围、预计回收量和备份位置；默认恢复插件环境并保留会话、API 配置。清空 API 配置属于单独的破坏性选项，须独立确认且支持恢复。
- G06.3：路径通过 realpath、目录包含关系和链接边界检查；在变更前停止有关进程、验证备份可读，失败回滚并做最小启动验证。磁盘不足时拒绝执行，不先删备份腾空间。
- G06.4：对 dsh-paperclip 建立版本明确的复现，再决定事件处理协调、兼容提示或隔离；不能凭单条投诉永久禁用第三方插件。R36 只作重复关联，不新增独立开发任务。

**验收：** 正常和失败安装后均可完成官方工具调用；插件停用可恢复，内置插件基线不减少。中断清理、目录越界、链接越界、磁盘不足、损坏备份均有安全终态。修复后会话数量、配置内容及插件清单符合预览；回滚后重新启动成功。第三方冲突需在固定版本组合下复现并验证处理结果。

**开源实现参考：** 将依赖身份诊断与事务恢复分别处理。

- 模块身份：参考 [pnpm 的符号链接依赖结构](https://pnpm.io/symlinked-node-modules-structure)，记录插件与宿主各自解析出的 SDK 路径、realpath、版本及必要的运行时身份比较，复现相同版本多副本与 peer dependency 组合。优先修正声明、打包 external 和现有挂载方式，不添加指向官方 checkout 的路径映射，不把全局 hoist 或改写 loader 当作默认修复。专项验证工具调度 Symbol 在实际宿主中的一致性。
- 事务恢复：参考 [SQLite 原子提交与崩溃恢复](https://sqlite.org/atomiccommit.html) 的“先保存恢复信息，再变更，最后提交”顺序，在现有插件事务与存档模块中核对事务 ID、阶段记录、备份校验和重启恢复入口。采用方式为恢复算法参考，不为此新增 SQLite；文件目录操作不能直接宣称具有数据库事务的断电原子性。分别测试进程中断、磁盘不足、Windows 文件占用和跨卷操作，注明可保证的故障范围；未完成事务的备份不能作为普通缓存删除。

## G07：代理配置与网络诊断

**范围：R07、R17、R30 的网络开关部分。** 复用现有环境变量解析，分阶段接入 Electron、Node 请求、安装器和插件运行时。

- G07.1：先测试环境变量启动、快捷方式启动和系统代理启动的实际路由，区分“进程未继承变量”“设置尚未生效”“请求由另一层发起”。日志不得输出含用户名和密码的原始代理 URL。
- G07.2：定义直连、系统、手动/PAC 配置与优先级，保持现有 CLI/env 行为可兼容；增加 API、更新/商店及可控插件流量的独立配置和连通性诊断。
- G07.3：按公开 SDK 能力声明可控制范围。插件自行建连或启动外部进程时，代理配置不等于强制网络隔离；每会话“禁止联网”必须映射到真实工具/沙箱权限，并区分模型 API 必需流量和工具网络访问。

**验收：** 通过受控代理端记录确认各类请求实际路由和 NO_PROXY 例外；不支持的传输层明确提示，不显示已生效。认证代理、失效 PAC、DNS 失败均超时可恢复且日志脱敏。只有权限验证通过时才提供每会话联网禁止开关，否则列为能力阻塞，不能交付无效按钮。

**开源实现参考：** [Undici EnvHttpProxyAgent](https://github.com/nodejs/undici/blob/main/docs/docs/api/EnvHttpProxyAgent.md) 展示按请求传入 dispatcher 的方式；[Electron session](https://www.electronjs.org/docs/latest/api/session) 提供 setProxy 及连接池清理接口。建议先列出请求发起方与可控层，再在可控的 Node 请求边界按有效配置复用 dispatcher，在 Electron 层等待 setProxy 完成后执行探测。Node dispatcher 不控制 Electron、外部进程或所有 SDK 请求，不能直接套用一份全局设置；ALL_PROXY、PAC 等支持须逐层验证。切代理时处理旧连接复用，closeAllConnections 可能中断在途流，必须先协调活动请求。复用已有 Electron/Node 能力，确需 Undici 时核对锁定版本与现有传输实现；以代理端实际请求记录验收，不以设置保存成功代替生效。

## G08：项目工作目录迁移

**范围：R29。** 先核对官方 Workspace 是否允许改路径；复用会话桥接和事务恢复机制，不直接改写路径派生的 ID。

实施目标为“检查新目录、预览关联影响、停止或等待相关任务、执行变更、验证与回滚”。如官方支持原地变更则使用公开 API；否则设计创建或复用新 Workspace 并重新关联项目的流程，旧历史维持原归属和可读性。文件物理移动不是默认动作，Git Worktree 与正在执行的任务需单独处理。

**验收：** 新目录不存在、无权限、目标已关联、迁移中断和旧目录丢失均给出可恢复结果；重复操作不重复建立关联；后续新任务确实在新目录运行，旧会话可读、可追溯，失败回到原映射。公开 API 不足时输出能力缺口及上游需求，不直接编辑官方会话数据库。

**开源实现参考：** [Git worktree 的 move/repair](https://git-scm.com/docs/git-worktree) 可用于设计 Git 元数据与项目目录之间的一致性检查。建议先区分普通目录、主工作树与链接工作树；只有用户明确选择物理移动且满足 Git 条件时，才考虑调用现有 Git，不能统一套用 worktree move。主工作树、包含子模块的链接工作树等有不同限制；repair 修复 Git 管理关联，不会修复 DSH Workspace ID。沿用 G06 的事务证据保存旧路径及映射，针对跨卷、外部工作树、旧目录消失和移动后中断分别验证，避免为了换路径复制整个仓库或拉取另一套工作区管理框架。

## G09：用户说明、技能与可发现性

**范围：R30 的说明与入口、R32、R33、R14 的余额显示。** 以现有功能契约为准完善产品文案，复用 Live Stats、宠物、任务看板和技能模块。

- G09.1：技能文档给出最小 SKILL.md、合法 name、非空 description、重复名称优先级、真实目录与符号链接发现限制，并显示发现失败原因。规则以 [skills.mjs](../apps/dsh-desktop/src/extensions/skills.mjs) 为准；发现入口忽略链接与导入 bundle 内拒绝链接是不同约束，分别说明。
- G09.2：余额仅在 provider 有实际数据接口时显示；费用估算、官方余额、账单价格时段和输出速率峰值分别标注。未知值显示未知，不能填零或伪造所有供应商余额。
- G09.3：增加宠物用途、任务看板关闭或返回对话、删除/归档/分支语义说明；对照官方当前行为验证，保留原有操作入口。

**验收：** 新用户按文档可导入一个合法技能，非法名称和符号链接案例有准确原因及可行处理方式；中文 description 合法。余额未知时不误导为零；峰谷计费与 TPS 峰值不混淆。通过键盘及鼠标均能找到看板退出与会话操作说明。

**开放规范参考：** 对照 [Agent Skills 规范](https://agentskills.io/specification) 编写技能样例及诊断，逐项核对 name、description 和目录关系。规范中的名称长度与目录名匹配等要求，不能未经检查就宣称本项目解析器已经执行；文档分别标明规范要求、当前实现和兼容缺口。先提供现有导入器可接受的最小样例与负例；若后续加强校验，补旧技能兼容策略，不能静默使已安装技能失效。该项只需现有解析器与少量文本样例，不引入另一套技能框架。

## 完成定义与证据

每个工作项必须附：原需求定位、复现环境、代码证据、采用的官方 SDK 能力、实现范围、测试结果和未覆盖场景。使用开源参考时同时记录来源版本、借鉴机制、适配差异、许可检查及依赖/资源增量；没有引入依赖则明确记录。证据标记为“已现场验证”“专项测试通过”“静态判断”“待能力验证”，不能只填“代码已写”。

1. 开发入口使用最小失败样例；实现后运行与风险对应的测试，不新增只重复源码的断言。
2. 核心功能变动按仓库规则更新 [功能基线](../scripts/feature-baseline.json)，运行 `pnpm feature-baseline:check` 与 `pnpm desktop:regression:e2e`；按改动补充类型检查、包测试、Runtime 支持和依赖一致性门禁。受资源或缺依赖阻塞的门禁保留失败/未执行状态，不能省略后声称完成。
3. 文档改动运行 `pnpm docs:check`；无 pnpm 依赖时可直接执行同一入口 `node scripts/verify-docs.mjs`。文档链接、无 emoji 和 README 双语契约按 [文档规则](AGENTS.md) 检查。
4. 打包现场验收至少覆盖真实 Windows；G03 须覆盖真实鸿蒙设备，G04 须覆盖两设备。没有所需设备时明确登记阻塞和接手条件。
5. 恢复、迁移、升级必须有失败回滚证据；修复有效且保全门禁通过后才进入“验收中”，对应用户场景通过后才改“已完成”。复合需求的所有子项通过才关闭父记录。
6. 测试证据与一次性快照归入 docs/archive 或既有 CI 产物；本文只维护目标、依赖与验收契约。功能发布或重置用户数据均有各自执行流程，文档完成不代表已执行这些动作。
