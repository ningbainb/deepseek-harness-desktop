# DeepSeek Harness Desktop 3.5.0 Runtime 与插件架构审计

## 审计结论

当前 3.4.0 已具备插件兼容性判断、操作串行队列、Runtime 停止与重启协调、配置快照、启动崩溃恢复、旧 Profile 可逆隔离和安装前 registry 预取。这些能力降低了单次插件故障的影响，但尚未形成 3.5.0 要求的 Runtime ownership 安全边界。

关键缺口是插件依赖解析仍发生在 Live Profile：安装、更新、删除和批量安装在 Runtime 停止后直接运行 pnpm，随后才检查插件身份和 bundle。现有失败恢复主要还原 `package.json` 与 `pnpm-lock.yaml` 并再次运行 pnpm，不能证明物理 `node_modules`、传递依赖和单例 Runtime 包完整恢复。Host compatibility 解析也会优先读取 Profile，因此受污染 Profile 仍可能影响 Host 版本事实。

## 当前事实

### Profile 创建与维护

- `ensureDesktopProfile()` 在应用启动准备阶段创建或修复 `profiles/desktop`。
- `profile.mjs` 生成 Desktop 管理的 bundle、依赖链接、patch、workspace 配置和链接账本。
- 当前 workspace 配置使用 `nodeLinker: hoisted` 与 `autoInstallPeers: false`。
- Desktop 管理包主要来自应用安装目录或应用依赖解析；社区插件记录在 Profile 的 dependencies 与 bundles 中。
- `pnpm-lock.yaml` 由 Profile 内的 pnpm 安装、更新和删除操作维护；仅有内置包时允许不存在。
- `node_modules` 同时承载 Desktop 管理链接和社区插件解析结果，是共享 Live dependency graph。

### 插件来源与入口

- registry 插件由 `PluginRegistry` 获取 npm manifest，正常安装先执行 `pnpm store add`。
- Full Access 支持不受 registry 信任链约束的 Git、HTTPS、本地或其他外部来源，并在安装后读取最终 package identity。
- 单个安装、更新、批量安装、删除、启停、Preset 导入和恢复由不同入口进入 `PluginManager`、`registerExtensionIpc()` 与 `DesktopPluginRecovery`。
- `createExtensionOperationQueue()` 与 `PluginManager.queue` 已提供进程内单 writer 语义，但没有跨崩溃的持久 mutation ownership。

### 兼容性

- `assessPluginCompatibility()` 已输出 `compatible`、`unknown`、`incompatible`，支持 Desktop、Runtime、Desktop API、能力、surface、Node engine 与 peer range。
- Main Process 的普通安装路径会要求 unknown 明确授权，并拒绝 incompatible；Renderer 的 `allowUnknown` 不能授权 incompatible。
- `resolvePackageVersion()` 当前先读取 `profileDir/node_modules`，之后仍把 Profile manifest 作为解析 anchor。它不满足 Host truth 必须来自应用安装 Runtime 的要求。
- compatibility 只验证候选 manifest 的直接声明，未验证安装后 lockfile 与物理依赖图中的直接或传递 protected package 冲突。

### Mutation 与恢复

- registry metadata 和 store 预热发生在 Runtime 停止前，这是可保留的低停机基础。
- `applyPrepared()`、`applyPreparedBatch()`、`remove()` 与 Full Access 安装仍直接修改 Live Profile。
- `createRuntimeMutationCoordinator()` 统一 stop、apply、ensureProfile、start、commit 和失败恢复，但没有持久状态机、独立 staging、原子目录切换或启动后图验证。
- `captureProfileSnapshot()` 只保存 manifest 与可选 lockfile；恢复会在 Live Profile 再次运行 pnpm，物理图不是字节级或目录级 rollback。
- `DesktopProfileBaselineQuarantine` 可以可逆隔离不可信 loader 输入和整个 `node_modules`，但它面向启动恢复，不是日常插件事务系统。
- `PluginRecoveryStore` 与 `DesktopPluginRecovery` 能记录已知可用快照、自动停用故障插件、安全模式和恢复事件，但不能恢复中途崩溃的依赖激活事务。

### UI

- 当前 Extension Dock 一级导航和恢复页面仍暴露较多维护概念。
- 已安装插件长期显示兼容 badge，卡片同时展示多个按钮和技术原因。
- 安装表单直接展示 unknown 与 Full Access 技术选项，错误与恢复信息密度高于普通用户需要。
- 已有 aria-label、Escape、live region、操作队列和窄窗口样式可作为重设计基础。

## 与 3.5.0 Definition of Done 的差距

| 范围 | 当前状态 | 结论 |
| --- | --- | --- |
| 统一 Package Ownership | 多个数组和 Set 分散定义 | 缺失 |
| Immutable RuntimeBaseline | 无冻结的应用安装 Runtime 快照 | 缺失 |
| Host truth 与 Profile 分离 | compatibility 优先 Profile | 不满足 |
| PnpmLockGraph | 仅字符串搜索 integrity | 缺失 |
| Protected Graph Validator | 仅顶层名称保护与候选 manifest 检查 | 缺失 |
| Staging Resolver | 只预热 store，解析仍在 Live Profile | 缺失 |
| Atomic Activation | Live Profile 原地 pnpm mutation | 缺失 |
| Persistent Journal | 恢复快照不是 mutation phase journal | 缺失 |
| Crash Recovery | 支持 Runtime crash，不支持 activation 中断恢复 | 部分满足 |
| Install/Update/Remove/Batch/Preset 统一事务 | 有共同 Runtime coordinator，mutation 实现仍分散 | 部分满足 |
| Legacy Profile Audit | 有链接修复与可逆隔离，没有 ownership graph audit | 部分满足 |
| PluginUIState | Renderer 仍组合兼容、更新与错误状态 | 缺失 |
| 简洁插件中心 | 当前页面高信息密度 | 不满足 |
| 真实隔离 fixture 与最终用户故事 | 现有测试未覆盖 protected transitive graph 与 crash phase | 缺失 |

## 实施边界与顺序

1. 建立统一 `runtime-package-policy`、冻结 `RuntimeBaseline`、分离 Host/Profile/Plugin 版本解析。
2. 建立当前 pnpm lockfile 的结构化解析、受保护依赖图与物理链接验证，不用 `pnpm list` 作为安全事实。
3. 建立同卷 staging、持久 journal、原子 activation 与启动恢复；先覆盖 install/update/remove/batch，再接入 Full Access 与 Preset。
4. 在 staging 与 activation 后各验证一次 protected graph；Runtime readiness 后才能 commit。
5. 用新的 integrity audit 自动修复 3.2 至 3.4 managed-link drift，无法安全修复时进入简洁 Recovery UI，保留全部用户数据。
6. Main Process 输出统一 PluginUIState；Extension Dock 收敛为已安装、发现、设置，技术信息只在高级详情和开发者模式展示。
7. 建立本地 tarball/Workspace pnpm fixtures、30 项 isolation unit matrix、Renderer UI 与 Windows 文件系统回归。
8. 在上述门禁与核心功能实机验证完成后评估 isolated linker；不兼容时保留 hoisted 并记录证据。
9. 最后将 Desktop 版本升为 3.5.0，生成正式本地安装包，核对 Runtime 清单、ASAR、签名状态、覆盖升级、打包后启动和核心内置插件。

## 数据与发布保护

- staging、rollback、repair 只操作 Profile 代码环境，不操作会话、Workspace、Provider、API Key、Memory、Personal Prompt、用户设置、插件数据或用户文件。
- transaction journal 只记录 transaction id、操作、插件标识、phase 和时间，不记录路径、密钥、Prompt 或用户内容。
- 在完成最终验收前不把现有 `3.5.0-beta.3` 视为 3.5.0 交付物，不创建 Release。
