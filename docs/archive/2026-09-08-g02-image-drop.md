# G02.2 packaged image-drop verification

Date: 2026-09-08.

## Scope and environment

This record covers G02.2 and the attachment part of R14/R34. The verified host
was the locally built Windows `win-unpacked` Desktop 3.3.0 package with Electron
43.4.0, official DSH/SDK 0.1.1-rc.1, and Node.js 24.19.0 for the test driver.
The test used a fresh temporary Desktop user-data directory, DSH Home, Workspace,
and Session. It did not modify an official DSH source checkout.

The application implementation continues to use the official Conversation
draft-image registry and input shell. No new runtime dependency was introduced.
The pica reference in the engineering goal was not adopted because the existing
Canvas pipeline met the functional limit after explicit decoder cleanup was
added; adding a second resampling dependency was not justified by this result.

## Implementation result

- Image headers, source bytes, source dimensions, and source pixels are checked
  before browser decode when the format exposes dimensions.
- Oversized images are processed one at a time through validation, decode,
  compression, submission, and cleanup. New batches, Escape, session teardown,
  and unmount abort stale work.
- Chromium now uses `createImageBitmap` and always calls `ImageBitmap.close()`.
  The previous `HTMLImageElement` plus object-URL path remains as a browser
  compatibility fallback and still clears `src` and revokes its URL.
- The intermediate Canvas is reset to zero dimensions in `finally`. Draft
  preview URLs remain owned by the official Conversation service and are
  revoked when the user removes the attachment.
- An intercepted oversized-image drop now emits the drag-end cleanup signal.
  This closes the official native attachment overlay, whose document listener
  cannot observe the capture-phase-stopped drop.
- The inlay exposes a read-only `data-phase` diagnostic. This does not change
  controls or attachment behavior.

## Packaged acceptance

`apps/dsh-desktop/scripts/verify-packaged-image-drop.mjs` generates fixtures in
memory and drives the packaged renderer through real DOM `DataTransfer` and
`DragEvent` objects. The final passing run used:

| Fixture or output | Bytes | Dimensions | Result |
| --- | ---: | ---: | --- |
| Oversized JPEG input | 10,713,877 | 2304 x 2304 | Accepted through the bounded pipeline |
| Compressed JPEG draft | 2,603,636 | 2048 x 2048 | Under the 3 MiB and 2048-pixel targets |
| Corrupt PNG-shaped input | 2,097,216 | Unknown | Failed, then accepted a valid retry without reload |
| Small native PNG | 266 | 64 x 64 | Accepted by the official native attachment path after a large image |

The same run passed cancellation followed by retry, 20 sequential oversized
image drops, and a final large-then-small sequence. Every successful preview
was removed before the next operation. The input remained enabled, the native
drop overlay returned to zero after every case, and all 24 observed object URLs
were revoked.

The source-size, pixel-count, dimension, unknown-dimension, serial-queue,
cancellation, Canvas failure, and explicit ImageBitmap-close cases are also
covered by the package tests. The final package result was 167 passing tests,
one skipped test, and a passing TypeScript check.

## Resource evidence

The first complete run used the `HTMLImageElement` decoder. Although all URLs
were balanced, its Electron working set rose from 982,659,072 bytes after five
operations to 1,127,223,296 bytes after twenty. The 144,564,224-byte retained
increase exceeded that run's 98,265,907-byte budget, so that run was retained as
a failure and prompted the ImageBitmap change.

In the final run, the four Electron-process idle medians after 5, 10, 15, and 20
operations were 908,984,320; 978,268,160; 1,050,214,400; and 977,084,416 bytes.
The sequence fell after operation 15 and ended 68,100,096 bytes above the first
group, below the 90,898,432-byte allowance (10 percent of the first group, with
a 64 MiB floor). The observed Electron working-set peak during active work was
1,181,204,480 bytes and the private-byte peak was 1,610,674,176 bytes.

The complete eight-process Electron plus DSH Host tree measured 1,259,892,736
bytes after operation 5 and 1,266,413,568 bytes after operation 20. Its sampled
high point was 1,405,165,568 bytes after operation 15, followed by a decrease.
These figures demonstrate that the repeated image scenario did not continue to
grow each round. They do not redefine the separate five-minute idle M0 baseline
or claim that active image processing stays within ten percent of an empty app.

## Remaining coverage boundary

The test is a packaged Windows automation with synthetic browser drag events;
an OS Explorer hand-drag and subjective rendering review remain release-machine
checks. Exact rejection at the hard 32 MiB and 32-million-pixel boundaries is
covered by unit tests rather than allocating those inputs twenty times in the
low-memory packaged run.
