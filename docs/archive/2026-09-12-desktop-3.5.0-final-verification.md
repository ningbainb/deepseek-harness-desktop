# DeepSeek Harness Desktop 3.5.0 最终验收记录

## A. Executive Summary

Desktop 3.5.0 已完成 Runtime ownership、受保护依赖图校验、同卷 staging、持久事务 journal、原子激活与回滚、旧 Profile 审计修复、插件管理 UI 收敛、安装进度说明、Preset 导出、原生终端路由、模型菜单收窄及打包版 Agent 工作回路等改造。

本地 Windows x64 安装包已从独立工作树构建，发布功能关闭，未创建 GitHub Release。包内 164 个 ASAR 文件和 121 个 Runtime 包通过完整性检查；打包应用冷启动、Workspace/Session 创建、模型选择、真实主界面发送、Agent `pwsh` 工具调用、最终回复、模型发现入口、ChatGPT OAuth 桥接及拓展坞入口均通过。

当前唯一不能记为通过的发布条件是真实 3.4.0 已安装环境上的完整覆盖升级。维护机保存真实安装和用户数据，且没有 Windows Sandbox 或其他可丢弃 Windows 主机；为避免破坏真实会话，本轮只执行了编译后的 NSIS 9 场景生命周期、3.4.0 direct-start fixture 和全新 Profile 验收。正式公开分发前仍应在可丢弃 Windows 环境补做一次真实 3.4.0 -> 3.5.0 覆盖安装。

## B. Root Cause

3.4.0 之前的问题不是单个插件按钮或一条版本判断，而是缺少统一的运行时安全边界：

1. Desktop 管理的 Runtime、支持包、内置插件、社区插件和可安全共享包分散在多处列表中，无法证明 ownership 不重叠。
2. 社区插件依赖直接在 Live Profile 中解析；失败后只恢复 manifest 和 lockfile，不能证明物理 `node_modules` 已恢复。
3. compatibility 曾可能从受污染 Profile 读取 Host 版本事实，候选 manifest 检查也不能发现传递依赖和物理 singleton 冲突。
4. 安装、更新、删除、批量、Full Access 和 Preset 虽共用 Runtime stop/start 协调，但没有跨崩溃的持久事务状态。
5. 插件中心把兼容性、恢复、更新和技术错误直接暴露给普通用户；主界面又叠加了重复的翻页、终端和面板按钮。
6. NSIS 文件写入与压缩阶段缺少阶段解释，用户看到长时间不动的进度条会误判为卡死；旧安装器失败时也没有可持续读取的阶段日志。

## C. Architecture

```text
Application installation
  |
  +-- Package Ownership Policy
  |     +-- Desktop Runtime
  |     +-- Desktop Support
  |     +-- Built-in Plugin
  |     +-- Shared Safe
  |
  +-- Immutable RuntimeBaseline
        +-- exact version
        +-- resolved path / real path
        +-- source ownership
        +-- SHA-256 fingerprint

Community plugin request
  |
  +-- metadata and compatibility admission
  +-- same-volume staging profile
  +-- pnpm resolution outside Live Profile
  +-- PnpmLockGraph and physical graph validation
  +-- Runtime stop
  +-- archive old Live environment
  +-- atomic activation
  +-- repair managed links and validate again
  +-- Runtime start and readiness
  +-- durable commit and cleanup
        |
        +-- any pre-commit failure: rollback archived environment
        +-- process crash: recover from active journal on next launch
```

Host compatibility facts only come from the immutable application baseline. The Profile and plugin graph are treated as untrusted mutation inputs until both lock graph and physical links pass validation.

## D. Ownership And Protected Packages

| Category | Owner/source | Replaceable by community plugin | Singleton default |
| --- | --- | --- | --- |
| `desktop-runtime` | Application Runtime | No | Yes |
| `desktop-support` | Desktop support layer | No | Yes |
| `builtin-plugin` | Bundled Desktop plugin | No | Yes |
| `community-plugin` | User-selected Profile dependency | Yes, inside its isolated graph | Plugin-defined |
| `shared-safe` | Explicit compatibility allowlist | No application replacement; nested copies allowed | No |

The registry rejects duplicate category claims. Protected package identity, version, source, real path and physical singleton count are checked against `RuntimeBaseline`. Root declarations and transitive lockfile nodes are classified separately so a plugin cannot hide a protected Runtime dependency behind another helper package.

## E. Transaction Flow

The persistent phases are:

```text
CREATED
-> METADATA_READY
-> COMPATIBILITY_APPROVED
-> PACKAGE_PREFETCHED
-> STAGING_READY
-> DEPENDENCIES_RESOLVED
-> GRAPH_VALIDATED
-> RUNTIME_STOPPING
-> OLD_ENV_ARCHIVED
-> NEW_ENV_ACTIVATED
-> MANAGED_LINKS_REPAIRED
-> RUNTIME_STARTING
-> RUNTIME_HEALTHY
-> COMMITTED
```

Rollback uses `ROLLING_BACK -> ROLLED_BACK`; a failure before activation may end at `FAILED`. The active marker is created exclusively, so only one dependency mutation owns the Profile. Staging and Profile must be on the same volume. The old environment is moved into an archive before the staged `node_modules` is renamed into place. Commit is written before cleanup; if cleanup is interrupted, startup recovery completes it idempotently instead of rolling back a healthy Runtime.

Install, update, remove, batch, Full Access and Preset package mutations use the same staging and Runtime coordinator. Preset configuration and dependency transactions declare an explicit commit order and both remain rollback-capable until Runtime health is proven.

## F. Legacy Migration

Startup reads only Profile manifest, managed links, lock graph and corresponding pnpm virtual-store nodes. It does not inspect chats, API keys, prompts or user files.

```text
audit
  +-- healthy: continue
  +-- uninitialized: build managed environment, then audit
  +-- repairable: reconcile managed links, then audit again
  +-- blocked: keep user data, stop plugin mutation, show recovery action
```

Automatic repair is limited to missing protected packages, protected version conflicts and protected source conflicts. An unsuccessful repair returns `PLUGIN_ENVIRONMENT_REPAIR_REQUIRED` with a bounded Chinese user message; raw paths and raw errors remain in local diagnostics.

## G. UI And Installer Changes

- Extension Dock keeps three understandable areas: installed plugins, discovery and settings. Compatibility health is quiet by default; technical details stay under advanced/developer disclosure.
- One mutation owns the action surface. Buttons are disabled while busy; retry, rollback and recovery states come from Main Process `PluginUIState` rather than Renderer-side guesses.
- Main-window duplicate floating turn navigation was removed; official Runtime navigation remains.
- Manual terminal opens the Desktop terminal first and focuses an existing panel on repeat; web PTY, Agent terminal and background-session behavior remain independent.
- Model menu is capped at 300 CSS px and removes long English descriptions while keeping provider grouping, full-name tooltip, selection, disabled reason and reasoning controls.
- Main-window panel toggles moved into `Tools -> Layout`; native right sidebar remains. Unknown DOM or missing native capability restores the original compatibility buttons.
- Preset save dialog uses Chinese title, file type and confirmation label. Export/import actions are serialized and visibly report waiting, cancel, success, failure and retry.
- NSIS reports preparation, file installation and commit/verification phases. Unquantifiable file work uses an activity indicator and elapsed time rather than a fabricated percentage. Each attempt writes a local diagnostic log and preserves rollback behavior if the progress observer fails.
- The 3.5 support prompt combines Star and Afdian support, is delayed behind existing startup dialogs and is displayed once per local user.

Evidence screenshots committed in `docs/screenshots/desktop-3.5.0-*`; fixture-only screenshots and local exploratory captures are not release inputs.

## L. Remaining Risks

1. Real 3.4.0 -> 3.5.0 overlay installation is not executed on this maintenance machine because the available installation and user directories contain real data. The compiled NSIS and fixture coverage substantially reduces risk but does not replace this final acceptance test.
2. The installer is unsigned. Windows reputation prompts and enterprise execution policies may differ from the local test environment.
3. The two skipped Node cases require Windows symbolic-link privilege. Their non-symlink equivalents and package graph paths passed, but a privileged Windows CI host should run them before a release candidate is promoted.
4. Cold startup measured 17.8 seconds on this machine. It is functional, but hardware, antivirus and first-use managed Git scanning can make the first launch slower.
5. The package was built from application commit `35609e6d97c7b3ae68d495e883c37dde71eb6463`; later branch changes only touch excluded verification and documentation files, so the packaged application payload is unchanged.

Release decision: suitable for maintainer testing. Do not describe the real 3.4.0 overlay as passed until it is executed on a disposable Windows environment with before/after chat, Provider, Preset, plugin, update rollback and uninstall evidence.
