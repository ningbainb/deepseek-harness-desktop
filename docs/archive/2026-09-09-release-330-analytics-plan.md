# 3.3.0 发布前埋点优化方案

## 目标与当前证据

围绕版本采用、功能使用与可靠性做发布分析。沿用 Cloudflare Worker + D1 + 现有登录管理看板，不接入会话内容采集 SDK。源码与第三方构建保持埋点关闭，正式构建由发布流水线注入端点。

代码核验发现：客户端允许一批 20 个 schema 3 事件，服务端仅允许 8192 字节，满批可能整批丢失；月度观察表主键没有版本，月内升级后的同类事件可能被首次版本覆盖；旧漏斗为独立阶段实例数，不能证明同一实例依次完成。方案先修正这些口径，再补 3.3.0 功能触点。

## 指标与决策

| 指标 | 定义 | 用途与限制 |
| --- | --- | --- |
| 版本采用实例 | 窗口内在该版本产生启动事件的稳定匿名安装实例去重数 | 对比 3.3.0 与其他版本；同一实例可以使用多个版本，各版本不能直接相加作为总用户数 |
| 功能触达与结果 | 按版本、固定功能、结果分别统计次数与实例数 | 区分反复操作和使用范围，发现文件添加、项目连接、拓展坞页面的失败点；阶段为独立观察，不声称有序转化 |
| 启动成功率 | ready 次数 / (ready + failed 次数)，仅使用 runtime_start_result | 同口径完成结果；同时展示分母，异常终止导致未上报的启动不在分母内 |

保留现有 D1/D7/D30 留存、下载点击、更新、性价比模式和时长指标。下载点击不等于下载完成或安装。进程存活时长不等于前台工作时长。没有成功交付信号时，不把文件添加或项目连接叫作任务完成。上线先观察七天基线，再制定业务目标，不虚构目标值。

## 第一阶段实现范围

1. 将服务端容量与既有 20 条批次匹配；客户端增加字节上限、内存队列上限、排空和退出截止时间验证。维持失败不持久化重试的既有契约，因此事件次数仍是可观测下界。
2. 新增按 UTC 日、稳定匿名实例、版本、事件、结果和固定细分去重的观察表，保留 90 天，仅接收新客户端 schema 4。保留旧表和 schema 2/3 的接收与存储边界。覆盖起点记录首次收到 schema 4 的 UTC 日，不用不可还原的月表伪造历史。
3. 增加项目新建/已有项目连接的尝试与结果、普通附件添加的尝试与结果、拓展坞六个设置页打开结果。文件名、类型细节、路径、目录名、错误原文均不上传。图片继续原生通道，本阶段附件指标明确仅覆盖普通文件队列。
4. 管理看板新增发布分析区，可选版本和 7/30/90 天，展示启动结果与功能实例/次数，提供聚合 CSV 下载。全局旧报表入口保留，新区明确展示数据覆盖起点及不完整窗口。
5. 沿用现有登录鉴权；新 API 只返回聚合结果。云端先迁移、后部署，核验旧协议兼容及新 API 鉴权；测试数据使用本地 SQLite，不向正式业务表注入假用户。

## 后续阶段

记忆采纳/引用、供应商配置验证、真实模型请求完成和跨日实际交互活跃可作为后续独立扩展。必须从真实业务结果触发，不用页面点击代替成功，不修改官方 DSH 源码。严格有序转化需要另行设计作用域及顺序契约，本次保持透明的阶段覆盖口径。

## 验收与发布顺序

客户端至 Worker 满批测试、白名单拒绝敏感字段、队列拥塞/退出、同日升级/跨月去重、旧 schema、SQL 实际执行、鉴权与看板交互测试通过；执行功能基线和桌面回归。线上核验账号、数据库、现有绑定及开关后只做增量迁移和兼容部署。桌面安装包必须重新构建后才含客户端改动；正式版本推送与发版是后续动作。

Cloudflare 数据库迁移遵循[官方迁移文档](https://developers.cloudflare.com/d1/reference/migrations/)，部署设置参考[官方配置文档](https://developers.cloudflare.com/workers/wrangler/configuration/)。本文件记录设计与本轮交付范围，不把计划视为已完成结果。
