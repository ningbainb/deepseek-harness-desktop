# Desktop 3.4.0 and DSH 0.1.5 implementation plan

## Objective

Prepare Desktop 3.4.0 against the exact official prerelease
`@deepseek-ai/dsh@0.1.5-alpha.1`, preserve every existing Desktop and plugin
surface, and promote the runtime only after the complete dependency graph,
source compatibility, regression suite, and packaged application are verified.

The registry version is written exactly as published. `0.1.5-alpha.1` is the
upstream package corresponding to the requested DSH 1.1.5 kernel line; it must
not be shortened to an ambiguous tag or range in Stable metadata.

## Evidence captured before mutation

- Stable branch: `main` at `95886c8`, equal to `origin/main` when the work began.
- Stable Desktop version: `3.3.0`.
- Stable DSH graph: exact `0.1.1-rc.1` packages, Cordis `4.0.1`.
- Stable focused Candidate and Runtime tests: 25 passed.
- Stable Desktop Node suite: 903 tests; 896 passed, five sandbox-only registry
  failures and one transient Electron helper failure in the first run; the six
  affected tests passed when rerun in their required environment. Two Windows
  symlink skips are expected.
- Candidate package metadata was read from the official npm registry on
  2026-09-09. The target is `0.1.5-alpha.1`, Cordis is `4.0.2`,
  `cordis-plugin-group` is `1.0.2`, and `schemastery` is `3.18.2`.
- A detached candidate worktree proved that a top-level-only DSH upgrade creates
  36 duplicate identity-sensitive runtime packages.
- `@deepseek-ai/dsh-client-runtime` and
  `@deepseek-ai/dsh-host-apiproxy` do not publish `0.1.5-alpha.1`. Keeping either
  package retains the old runtime graph. Removing both in the isolated worktree
  restored the single-version invariant for all 58 checked packages.
- The first complete 0.1.5 type matrix found 18 failing workspaces and four
  passing workspaces. Failures group into client store/context ownership,
  settings registration, Session journal changes, remote Gateway migration,
  and dependency identity drift.

## Ordered work

### 1. Candidate graph correctness

- Discover every official DSH SDK declaration across all workspace manifests.
- Resolve exact candidate package identities, not only the top-level package's
  peer dependencies.
- Reconcile Cordis and other official companion packages from candidate
  manifests.
- Fail before mutation when a workspace still references a retired SDK entry
  point.
- Keep the Candidate workflow isolated from Stable.

Acceptance: candidate-planning tests pass and a retired package produces an
explicit migration blocker instead of a mixed-version install.

### 2. Client API migration

- Replace `dsh-client-runtime` Context imports with Cordis `Context`.
- Move settings contracts to `dsh-client-ui-settings/client`.
- Move snapshot and engine stores to `dsh-client-store`.
- Move Session and Workspace identities to `dsh-client-connection/client`.
- Move Session projection contracts to `dsh-api-session-controller/client`.
- Remove the retired client runtime from manifests, client injection metadata,
  build externals, Desktop boot lists, runtime evidence, and SDK tests.

Acceptance: no production or generated artifact references the retired client
runtime, all affected package typechecks and tests pass, and client bundles keep
the shared store external.

### 3. Settings and Session model migration

- Register plugin settings with `ctx.settings.installSection` and validated
  literal namespaces.
- Migrate Session persistence reads from embedded `session.events` to the
  official observation and journal APIs.
- Update surface replacement coordinates from `start` and `end` to
  `startSeq` and `endSeq`.
- Replace removed `assistant/chunk` assumptions with the 0.1.5 assistant stream
  contract while retaining completed message rendering.
- Align Zod and Schemastery versions so typed projection schemas have one
  physical identity.

Acceptance: compatibility, live statistics, pet, memory, scheduler, import, and
conversation tests pass without weakened assertions.

### 4. Remote API migration

- Replace `dsh-host-apiproxy` with the official Typert Gateway and the session,
  workspace, settings, and remote assembly packages.
- Preserve pairing, per-request user-scope authorization, revocation checks,
  bounded history, model selection, workspace filtering, and live mobile
  updates.
- Keep remote failures redacted at the mobile boundary.
- Update mobile wire types and validation from official 0.1.5 contracts.

Acceptance: the retired host proxy is absent, remote-web-ui typecheck and tests
pass, unauthorized resources remain indistinguishable, and mobile live/poll
fallback behavior is covered.

### 5. Compatibility patch review

Evaluate every registered patch against 0.1.5. Port a patch only when its
regression still reproduces; otherwise remove it only after the documented
removal condition and referenced regression pass. In particular, re-check:

- Windows subprocess `windowsHide` behavior.
- Provider `toolsCapability` handling for models without tool support.
- The settings models content slot.
- Queued turn continuation, cancellation presentation, tool-call argument
  envelopes, skin profile isolation, startup corruption, and transcript tool
  balance.

Acceptance: every patch has an explicit retain, port, or verified-remove result
in generated runtime evidence.

### 6. Version and support evidence

- Set Desktop and root release versions to `3.4.0` only after source migration
  passes.
- Pin all runtime identity-sensitive packages exactly.
- Update the runtime support source, known-good evidence, support matrix,
  coupling audit, release notes, website, documentation pairs, and feature
  baseline where the runtime graph or visible contract changed.
- Keep candidate status separate from supported or known-good status until the
  complete release gate passes.

### 7. Final verification

Run with Node 24 and publishing disabled:

1. focused package typechecks and tests after each migration batch;
2. `pnpm feature-baseline:check`;
3. full workspace typecheck and unit tests;
4. script, dependency, runtime graph, import boundary, coupling, support,
   aggregate, gallery, website, release-note, and documentation checks;
5. `pnpm desktop:regression:e2e` and required focused Electron regressions;
6. local Windows directory package, package verification, and packaged smoke;
7. process-tree cleanup check proving no Runtime process remains.

Desktop 3.4.0 is ready only when failures are zero apart from explicitly
documented platform skips, the packaged runtime resolves one exact graph, and
the working tree contains no unrelated user-file changes.
