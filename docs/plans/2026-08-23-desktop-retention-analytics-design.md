# Desktop 留存率与使用时长分析设计

## 目标

在现有 Cloudflare Worker、D1 和正式 Desktop 匿名埋点之上增加 D1、D7、D30 留存率，并在现有管理看板展示留存与使用时长。用户无需打开网站或配置埋点；只有官方打包流程写入遥测端点。源码、开发和第三方构建继续保持关闭。

## 方案选择

采用本地随机秘密派生的稳定匿名安装哈希。每日和每月匿名值继续用于 DAU、MAU、地区、版本和漏斗去重；新增稳定哈希只用于安装首见日期和按日活跃集合。它不使用 DSH 账号、ChatGPT 登录、机器码、硬件信息或 IP，也不上传本地秘密。

不采用客户端自行计算“第几天回访”事件，因为客户端状态删除、系统时间变化和漏报会让口径不可审计。不采用账号 ID，因为新用户可能没有账号，而且会扩大身份数据范围。稳定匿名安装哈希是计算跨日留存所需的最小长期关联键。

## 数据流与兼容性

Desktop 遥测协议升级到 schema 3，每个固定事件增加 `installationActor`。Worker 同时接受现有 schema 2，避免已发布的 3.0.2 客户端在 Worker 更新后停止上报；只有 schema 3 的 `app_launch` 进入留存表。

D1 新增首见表和每日活跃表。首见表对匿名安装哈希执行 `INSERT OR IGNORE`，每日活跃表按 UTC 日期去重。管理 API 在选定周期内生成每日 cohort，并只对已经成熟的 cohort 计算 D1、D7、D30；尚未到观察日的 cohort 返回空值，不误记为零留存。两张表保留 400 天，定时任务自动清理。

## 看板与使用时长

管理看板增加 D1、D7、D30 加权留存卡片和 cohort 表。加权口径为成熟 cohort 的留存人数之和除以 cohort 人数之和。使用时长使用现有 `app_session_end` 固定区间，不上传精确时长：5 分钟以内、5 至 30 分钟、30 至 120 分钟、120 分钟以上。

## 故障边界与验证

遥测始终为 best effort：网络、D1 或管理看板失败不得影响 Desktop 启动、退出和更新。Worker 对 schema、字段和枚举继续严格校验，不保存原始请求。发布前覆盖客户端身份稳定性、schema 2 向后兼容、schema 3 写入、cohort 成熟度、使用时长查询、定时清理、管理页面内容和正式包配置。验证通过后执行远程 D1 migration，再部署 Worker，最后读取部署信息和线上 HTTP 状态确认生效。
