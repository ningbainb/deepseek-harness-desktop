# Desktop 测试质量改进完整方案

状态：实施中。适用范围是当前工作区的 Desktop 3.5、macOS arm64 开发线，以及需要保全的 Windows 行为。T01、T02、T03 的首版和 T06 已落地；候选完整回归当前为 28/29，macOS 27 原生最小化是剩余阻断。

## 1. 决策与目标

保留有效测试，按风险补齐和改造；不整体重写，也不以套件数量或通过率证明产品可靠性。目标是让维护者能回答：测了哪个产物、覆盖了哪些用户风险、哪些没有验证、失败能否复现，以及这个候选版本是否满足明确的发布门槛。

现有测试能抓到退出、持久化、布局、迁移和工具执行等真实问题，应当作为基础继续使用。当前 29 是 mac 平台筛选后的调度单元数，其中混有应用流程、专用夹具和单元集成，不是 29 个完整用户旅程。前轮“28/29”是整轮执行与后续复测的汇总，不能解释为一次完整运行全绿，更不是功能覆盖率。

本方案的完成标准：

- 每个必须保全的核心能力有稳定需求 ID、适用平台、正向和关键失败场景，以及明确的验收证据。
- 源码、组件夹具、安装包、实际安装环境和人工验收分别记录，不互相替代。
- 测试结果绑定真实产物和测试版本；旧包、未执行、超时、跳过、重试成功不能被误计为首次通过。
- 数据保全、授权隔离、启动退出和迁移恢复等关键路径能通过有意注入故障证明测试确实会失败。
- 当前 macOS 原生最小化失败保留为未解决项；在 macOS 15 云端成功，也不能自动关闭本机的问题。

| --- | --- | --- |

尚需在阶段 A 完成：逐断言审查、所有独立脚本的真实可运行性确认、漏测场景盘点、各 runner 的耗时与不稳定性基线。不能把尚未读到某项检查直接等同于仓库完全没有该能力的测试。

## 3. 测试分层和门禁职责

| 层级 | 测试对象 | 主要职责 | 运行位置 |
| --- | --- | --- | --- |
| L0 静态与保全 | 当前仓库和依赖图 | 类型、公开契约、SDK 边界、挂载和功能清单、文档 | 每个 PR |
| L1 单元与服务集成 | 纯逻辑、文件系统、局部真实服务 | 状态机、并发、回滚、权限、错误处理 | 每个 PR |
| L2 组件与应用适配 | 专用夹具或源码应用，明确区分 | 布局、慢资源、事件时序、窗口适配 | 每个 PR，按平台 |
| L3 打包体用户流程 | 当前候选 .app/.exe 的真实 Runtime | 启动、会话、终端、插件、持久化和恢复 | PR 核心子集；夜间完整 |
| L4 安装与升级 | 最终 DMG/ZIP/安装器 | 解包、安装位置、覆盖升级、回滚、隔离和系统集成 | 候选发布及打包链变更 |
| L5 真机人工与外部服务 | 原生 UI、第二台设备、可选真实 API | IME、权限旅程、显示器、实际 LAN、外部协议兼容 | 候选发布或相关能力变更 |

L2 和 L1 可以与完整发布检查一起运行，但报告必须保留层级和真实测试对象。L3 中的应用流程使用真实桌面和 Runtime；模型可以是受控的本地协议服务，不能因此声称已验证真实供应商的全部行为。

保留 Node test、现有 Vitest 与 Playwright library。第一阶段不强制迁移全部脚本到 Playwright Test。当前独立 Node 脚本不会因为新增 playwright.config 就自动获得重试、附件和追踪能力；先通过公共夹具接入 BrowserContext.tracing，随后仅迁移确实能获益的 UI 流程。

## 4. 执行器与测试清单设计

### 4.1 单一清单

apps/dsh-desktop/scripts/regression-suites.mjs 是当前运行清单的事实源；现有脚本和 pnpm 命令通过兼容入口调用。当前首版字段如下，后续阶段继续补齐 owner 与需求映射：

    {
      id: "desktop.window.chrome",
      tier: "application",
      targets: ["source", "packaged"],
      platforms: ["darwin-arm64", "win32-x64"],
      gates: ["pr-core", "nightly", "release"],
      requirements: ["window-chrome.caption-clearance"],
      script: "scripts/verify-window-chrome.mjs",
      args: [],
      timeoutMs: 180000,
      cleanupTimeoutMs: 15000,
      requires: ["gui-session"],
      network: "loopback-fixture",
      owner: "desktop-platform"
    }

具体 owner 在阶段 A 绑定到实际维护者。清单校验必须拒绝重复 ID、缺失脚本、未知平台、无目标声明、无清理预算的进程型测试，以及核心需求没有验收映射的情况。

package.json 的独立验收命令也要对账。未纳入统一门禁的命令必须有分类、原因和运行位置，例如真实外网检查或需要一次性机器的安装测试；不能仅因存在命令就计入已覆盖。

### 4.2 明确选择测试对象

- 核心源码检查显式选择 source；不得因目录里恰好存在 dist 而切换对象。
- packaged 模式要求明确的候选产物和来源验证；缺包、错架构或来源不符直接失败。
- fixture 模式必须明确显示夹具名称，不能把 source/fixture 的成功算作 packaged 成功。
- 旧版本兼容检查显式使用 legacy-artifact 模式，与当前候选验收分开。
- 拒绝未知参数、互斥参数和使测试静默切回源码的环境变量组合。保留既有入口的兼容适配，给出可解释的错误，而非静默改变行为。

### 4.3 状态与结果语义

每次执行保留 passed、failed、timed-out、blocked、skipped、not-run、interrupted 状态；每次重试记录独立 attempt。flaky 表示同一产物与同一测试版本下首次失败、复测成功，不能覆盖首次失败记录。

blocked 只用于已经验证的前置条件不满足，例如没有图形会话；不能因为暂时解释不了断言失败就归类为环境问题。平台不适用的 skipped 必须有清单规则和具体原因；适用的必需场景被跳过，门禁仍失败。

既有维护者批准的版本限定例外保留原约束，显示为 acceptedIssue，不能计入普通 passed。不得把历史 3.4.0 的例外放宽到其他版本。新例外需要维护者明确决定，不由测试代码自动生成。

### 4.4 超时、清理与证据

执行器设置单步、套件、清理三个预算。预算先采用现有合理上限，取得耗时分布后再调整，不能用无限等待或普遍加长超时掩盖问题。

每个套件结束后先写报告和保存失败证据，再清理。超过清理期限仍存在本次测试的进程、监听端口或文件锁，记为清理失败。keep-going 可以继续独立失败后的测试；如果隔离环境已无法保证干净，停止后续项并明确标记 not-run。

进程回收不能只依赖杀父进程或 POSIX 进程组：DSH Runtime 可能创建独立进程组。公共夹具需要保存本次启动的 PID、启动时间、可执行路径、父子关系及运行标识，结合退出前快照处理独立 Runtime。发送终止信号前验证身份，防止 PID 重用误杀。不得使用按应用名称全局清理的方式。

失败证据至少包括：步骤、错误、截图、trace（适用时）、脱敏的 Runtime/桌面日志、控制台异常、关键网络状态、进程清理结果和产物标识。日志容量需要上限并标记截断；证据写入失败本身不能被隐藏成成功。

### 4.5 报告结构

执行器在 artifacts/desktop-tests/<run-id>/ 下生成原子写入的 report.json 和逐套件日志。完整计划先写入报告，运行中持续更新；执行器被中断时也能看出哪些尚未执行。可读摘要和更完整的中断信号处理仍待后续阶段实现。

    {
      schemaVersion: 1,
      runId: "...",
      sourceRevision: "...",
      sourceDirty: false,
      sourceDigest: "...",
      testDigest: "...",
      artifactDigest: "...",
      mode: "packaged",
      platform: "darwin-arm64",
      osBuild: "...",
      toolVersions: {},
      planned: [],
      results: [{
        suiteId: "...",
        target: "packaged",
        attempts: [{
          status: "failed",
          durationMs: 0,
          errorCategory: "assertion",
          evidence: [],
          cleanup: { status: "passed" }
        }]
      }],
      gate: { status: "failed", reasons: [] }
    }

修复后复测必须生成新记录，并关联原失败。测试代码、应用代码或产物变化后，不能把多个运行拼成一次“全部通过”；可以显示跨运行的当前处置状态，但必须同时呈现原始运行结果。

## 5. 产物来源与构建完整性

在打包流程增加构建来源记录，覆盖应用源码、共享源码、工作区插件源码及构建输出、锁文件、pnpm 配置、补丁、打包配置、Runtime 支持文件、Node/pnpm/Electron/SDK 版本、架构与构建命令。采用排序后的相对路径和文件内容摘要，避免仅依赖提交号、版本号或修改时间。

本地工作区允许 dirty 构建，但必须计入未提交及相关新增文件；发布 CI 要求可追溯的干净提交。测试代码的摘要单独保存，不能与被测应用摘要混为一谈。

构建顺序为：冻结依赖安装、构建工作区包、确认共享产物一致、打包、校验、生成候选摘要、测试同一候选。只给未重新构建的旧 lib 加上新的源码指纹不构成可靠来源证明。

应用内来源文件记录构建输入；应用外候选清单记录实际 .app/.exe、DMG/ZIP/安装器及来源文件的摘要，避免自包含哈希循环。候选测试前后确认产物未被覆盖；多个测试可以使用不可变候选的独立副本，不能在验收过程中重新生成同名文件。

第一步可以先落实应用源码与包内源码比对，明确标记“仅校验桌面壳”；在工作区插件、锁文件和补丁也纳入前，不得声称整个产品的构建来源已经完整验证。

## 6. 公共夹具与断言规范

公共夹具负责启动、隔离、语言设置、就绪、证据采集和退出，不负责替业务断言作结论。每个测试尝试使用独立数据目录、DSH_HOME、DSH_AGENTS_HOME、端口和测试账户。对子进程建立可解释的环境变量白名单，阻止无关真实供应商 Key、SSH 凭据和遥测配置进入普通测试。

自动化禁止修改真实 ~/.dsh、系统协议关联、默认应用或用户 Keychain。涉及这些状态的 L4/L5 验收放在一次性用户/VM，或有明确授权、前后记录和恢复步骤的真实设备上。用内容摘要和相关文件集合验证隔离，不能只检查顶层目录 mtime。

UI 语言在应用文档创建前固定；至少覆盖中文与英文关键流程。使用预先设置的夹具关闭可选宣传提示，但首次使用引导必须另有完整用户路径验收。

断言约定：

- 使用可访问名称、角色或稳定语义属性定位；复杂页面逐步引入小型页面操作封装，避免巨大通用基类。
- 对异步状态等待可观察条件，例如持久化完成、窗口事件或任务状态，不把固定休眠当作成功依据。等待上限必须保留。
- 普通用户路径使用正常点击和键盘操作。强制点击、DOM 直接调用、内部 RPC 可以用于准备数据和针对性集成测试，必须在清单标明边界。
- 每个核心写操作至少验证 UI 反馈、磁盘/服务持久化、重新启动后的读回；失败路径验证未发生部分提交。
- 负向测试先验证前置条件确实成立，再检查拒绝原因和状态保全。任何错误都发生不能等同于正确拒绝。
- 不为保留测试通过而移除页面错误、放宽断言或更改必需功能。必要的平台差异明确表达，保留其他平台的原断言。

验证测试本身的能力：针对候选混用、结果状态、清理、授权、回滚和数据保全做受控故障注入。只修改临时夹具或使用依赖注入，不修改官方 DSH 源码 checkout。删除一次持久化、模拟一次错误授权或回滚中断时，对应测试必须稳定变红，恢复实现后变绿。

## 8. 补充覆盖矩阵与风险优先级

P0 是数据丢失、越权、无法启动/退出、不可恢复升级等发布阻断风险。P1 是主要功能失效和关键原生交互错误。P2 是次要体验、长尾兼容与优化。该分级约束执行顺序，不表示允许主动删除低优先级功能。

| 领域 | 优先级 | 必补场景与判定证据 | 验收方式 |
| --- | --- | --- | --- |
| 用户数据保全 | P0 | 会话/附件/工作区在升级、失败回滚、异常退出后内容摘要和关联关系不丢失、不重复 | 服务集成 + 打包体 |
| 插件生命周期 | P0 | 安装/更新/卸载成功；不兼容、缺包、断网、崩溃中断及回滚；旧插件和 Runtime 健康恢复 | 本地仓库夹具 + 打包体 UI |
| 权限与隔离 | P0 | 未授权设备、错误工作区、撤销令牌、跨用户资源、路径穿越被正确拒绝，且无部分写入 | 服务集成 + loopback 打包体 |
| 启动与退出 | P0 | 首启、二次启动、启动中取消、Runtime 崩溃、卡死、重复启动、退出残留 | 打包体 + 受控故障 |
| 安装与升级 | P0 | 实际安装位置、替换升级、中断恢复、旧版本用户数据和多份应用并存 | 一次性 mac/Windows 环境 |
| 消息与模型异常 | P1 | HTTP 401/429/5xx、断流、慢响应、停止生成、迟到结果、模型失效、工具失败 | 本地协议服务 + 普通 UI |
| 任务看板和 Git | P1 | 用户创建任务、worktree、执行、状态同步、冲突、取消和清理；原仓库数据保全 | 纳入现有 worktree 脚本并补缺口 |
| 图像理解 | P1 | 支持/不支持图片的模型分流、能力开关、压缩、失败后草稿保留、请求次数 | 纳入既有适配脚本并验证来源 |
| 插件代理 | P1 | GUI 配置对应实际安装流量，错误代理恢复、超时和取消 | 纳入既有脚本；需网络的部分独立标明 |
| 导入与技能 | P1 | 从支持格式导入、重复导入、损坏记录、能力加载/失效、取消 | 既有独立脚本审查后接入 |
| 原生 mac 交互 | P1 | IME、快捷键、窗口、菜单、显示器、系统权限、睡眠唤醒 | 自动化 + 真机人工 |
| 手机远程真实 LAN | P1 | 第二台设备完成配对、操作、撤销、断网恢复及跨工作区拒绝 | 真机人工或独立设备环境 |
| 长时间资源稳定性 | P1/P2 | 多次会话/面板/终端开关后，内存、句柄、FD、进程和监听端口趋势有界 | 夜间耐久检查 |
| 视觉与辅助使用 | P2 | 键盘导航、焦点顺序、缩放、深浅色、常见皮肤和可读性 | 自动断言 + 人工检查 |

loopback 授权检查不能冒充真实 LAN 通过；合成旧 Home 不能冒充完成了真实安装器升级；构建元数据中的最低系统版本不能冒充已经在最低系统上运行过。

## 10. CI 与执行矩阵

下表是拟实施策略；当前工作区的 macOS 15 CI 配置尚不代表已在远程执行成功。GitHub 托管测试机不要求开发者本机安装相同系统。

| 时机 | 必需检查 | 平台与资源 |
| --- | --- | --- |
| 每个 PR | L0/L1、关键 L2、当前打包体核心旅程、结果完整性 | Windows x64 + macOS 15 arm64 |
| 相关目录变更 | 插件、会话、权限、打包、窗口等对应专项 | 在基础必需检查上叠加，不能仅靠路径过滤省略基础门禁 |
| 夜间 | 全部适用自动化、并发/失败注入、耐久、较新 macOS 对照 | Windows + macOS 15；较新稳定 macOS 按官方 runner 可用性接入 |
| 发布候选 | 同一最终候选完整门禁、真实安装升级、人工专项、缺陷审查 | 所有声明支持且适用的平台；缺少环境明确记录 |
| 外部真实服务 | 小规模官方 API/SSH 等可选契约检查 | 单独手动任务，明确额度、密钥和网络目的地，不进入普通 PR |

公开仓库普通 PR 不接触真实模型 Key。不得通过 pull_request_target 加载不可信 PR 代码后提供密钥。CI 默认最小权限，不发布 npm、不上传安装包到正式 Release、不自动合并。

每个 job 先运行便宜的静态检查；候选构建一次后进入打包验收。每台机器同一时刻只运行一组需要原生窗口焦点的 E2E；单元测试可以有限并发。真实安装、磁盘/权限故障等破坏性检查放在独立一次性环境。

初始规划预算：快速逻辑检查 10–15 分钟、PR 核心含构建 15–30 分钟、夜间完整 45–75 分钟、发布候选自动部分不超过 90 分钟/平台。它们是待阶段 A 校准的工程目标，不是已测性能或服务保证。对超预算用拆分、缓存和独立机器处理，不能默认删场景。

当前产物最低系统声明为 macOS 12，而拟议云端主检查为 macOS 15。要宣称完整覆盖最低系统，需要另有可获得的 macOS 12 环境证据；缺少时明确写出覆盖空白。调整产品支持范围是单独的维护者决策，不能为了测试方便静默收窄兼容范围。

## 11. 分阶段交付与验收

按一名熟悉仓库的工程师估算，基本实施约 18–28 个工作日，另需 1–2 周夜间观测窗口；硬件、云端权限和维护者评审等待不计入人日。不是“模型运行时间”，也不承诺所有硬件组合在该期限内完成。阶段 A 结束后依据实测重新估算。

| 阶段 | 估算 | 交付物 | 退出条件 |
| --- | --- | --- | --- |
| A：完整盘点与风险对齐 | 2–3 日 | 29 项逐断言审查、独立脚本清单、需求映射、环境和耗时基线 | 每项明确对象、边界、前置条件、负向场景和 owner；所有 P0 缺口有任务 |
| B：执行器与结果可信度 | 3–4 日 | 单一清单、模式校验、逐次报告、期限、失败留证、结果完整性检查 | 受控的失败/超时/跳过/中断不会显示成功；未执行项可见；清理异常可检测 |
| C：候选来源与公共夹具 | 3–5 日 | 构建来源、候选摘要、统一启动/退出、隔离和脱敏、源码/打包目标修复 | 故意给旧包、错误架构、污染环境或残留进程时稳定阻断；正确候选通过 |
| D：核心用户路径与缺口 | 5–8 日 | 29 项针对性增强、补入 P0/P1 独立脚本与缺失场景 | 关键数据和权限故障注入能被抓住；所有 P0 自动场景有真实执行记录 |
| E：mac/Windows CI 与发行专项 | 3–5 日 | 云端矩阵、安装升级、mac 人工验收模板、候选结果汇总 | 适用的必需平台和安装路径有证据；本机原生失败有结论或明确阻断状态 |
| F：稳定性观测与维护交接 | 2–3 日 | 首次通过率、时长、故障检出能力、耐久趋势、维护规则 | 至少 5 次独立干净核心运行无非预期失败，并完成观测窗口内问题闭环 |

阶段依赖为 A → B → C → D → E → F。CI 和人工清单设计可以提前准备；正式通过结论必须等待来源绑定和环境隔离完成。

建议以小批变更交付：清单/报告、执行器失效保护、来源/夹具、源码与打包目标修复、数据与插件、用户旅程、mac 安装与原生行为、CI 与交接。每批保留兼容入口，运行相关测试及仓库强制门禁。原测试移入公共夹具时，先保留原路径并确认断言逐项对应，禁止一次性删除旧测试换成更弱的新测试。

## 13. 发布判定与维护指标

发布通过必须同时满足：

1. 候选来源与摘要验证通过，测试对象明确，整个验收期间未被替换。
2. 当前候选在所有必需且适用的平台完成检查；没有未执行的 P0、未知失败或未处理的清理失败。
3. P0 故障注入全部能检出目标错误，恢复代码后对应场景通过。
4. 必需的真实安装与 mac 人工验收完成，发现的问题有明确处置。
5. 重试记录完整；关键场景不通过自动多次重跑来“刷绿”。任何例外都有维护者批准的范围、原因、版本和到期条件。
6. 仓库既有功能保全、SDK 使用、文档和回归门禁继续满足；本方案不替代这些约束。

维护仪表仅使用可解释指标：必需场景执行覆盖、首次通过率、同版本 flaky 次数、故障注入检出情况、清理残留数、失败证据完整率、套件耗时 p50/p95、线上遗漏缺陷与对应新增回归。需求覆盖率的分母是已审定的场景清单，不能采用套件总数。代码覆盖率用来寻找可疑空白，不统一追求一个任意百分比。

连续 5 次通过是初始稳定性检查，不是无缺陷证明。数据、权限和启动退出模块的修改应直接触发相应负向测试；线上故障复现后先加入能失败的最小回归，再修复并保留。

## 14. 当前下一步与外部依赖

本轮交付的是方案，尚未开始实施上述阶段，也未进一步调用真实 API。用户此前提供的 Key 不进入文档或普通测试配置。

下一步首先执行阶段 A，然后实施 B/C；应优先让整个测试体系的结果可信。补充业务场景在其后按风险推进。原生最小化保持单独缺陷，不以换系统跑通代替修复本机体验。

远程 CI 需要允许的仓库推送/PR 流程和启用 GitHub Actions。当前没有把此前的公开推送确认视为已经获得。真实 LAN 需要第二台设备，显示器和 IME 等需要相应真机条件；无环境就记录未验证并影响发布判定。签名、公证和正式发布继续按维护者授权单独处理。
