# Desktop 2.2 Startup Hardening Design

DeepSeek Harness Desktop 2.2.0 will close two upgrade/runtime gaps without weakening the existing ownership guard. On Windows, Desktop currently launches the DSH runtime from the GUI-subsystem Electron executable. Although the direct runtime and ordinary subprocess seam request `windowsHide`, a descendant that does not preserve that flag can still create a visible console. Desktop will therefore launch the Windows runtime through Windows PowerShell with a hidden console and an encoded, single-quoted command. The wrapper remains attached, forwards the runtime's standard streams, waits for the runtime, and propagates its exit code. The controller continues to own and terminate the complete process tree. Non-Windows launch behavior remains unchanged, and individual child-process call sites retain `windowsHide` as defense in depth.

The 2.1.0 profile failure is handled through legacy ownership attribution. A profile may contain a regular pnpm materialization without a `.dsh-desktop-links.json` ownership record. Desktop may adopt it when package identity matches and either the installed version equals the packaged version or the earlier profile explicitly declared that dependency. It then creates the packaged managed link and writes the normal ownership record. An unattributed directory with a conflicting version still triggers the protective refusal, so arbitrary user-controlled content is not silently overwritten.

Installer cleanup begins with real executable-path attribution for the previous Desktop executable and its `resources` tree. It then snapshots Windows parent-process relationships and expands from those verified roots to descendants, covering community plugin CMD, PowerShell, Node, and package-manager prepare work even when the descendant executable lives in a system directory. Descendants are stopped before roots. Name-only matching remains forbidden, and a detached orphan without a surviving ancestry chain is deliberately left alone because it cannot be attributed safely.

The runtime persists its last successful loopback port in the isolated profile. At application bootstrap Desktop probes that port and reuses it only if it is bindable; otherwise it passes port zero and stores the newly allocated ready port. Plugin recovery also moves from mention-based matching to causal attribution: only explicit load failures or importer/stack paths inside an active community package can trigger isolation. Host failures, port conflicts, and incidental plugin-name log lines create diagnostics but preserve the plugin set.

Release gates will exercise a real 2.1-shaped profile fixture, incompatible-package refusal, attributed installer descendants, preferred-port selection, false-positive plugin logs, Windows hidden-wrapper construction, runtime stream/exit propagation, and the packaged runtime patch. Release metadata and notes will move to 2.2.0 only after targeted and full test suites pass.
